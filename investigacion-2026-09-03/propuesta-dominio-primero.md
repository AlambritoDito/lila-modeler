# Lila Modeler — propuesta "Dominio primero": un archivo canónico, tres contratos JSON, un motor propio

**Ángulo**: Domain first. Fijar con cuidado las siete cosas caras de cambiar (identidad de elemento, identidad y versión de proceso, namespace de extensión, modelo de escenario, contrato del motor y de resultados, layout de archivos, forma de las operaciones que exponen CLI/REST/MCP) y hacer todo lo demás de la manera más barata posible. El simulador es el módulo #1; los módulos #2..#N se enganchan a esos contratos, no al código del simulador.

## Resumen

Lila Modeler MVP = un monorepo pnpm en TypeScript con cuatro paquetes (`core` contratos, `bpmn` parser, `sim` motor DES puro, `cli`) y una SPA React + bpmn-js que corre el motor en un Web Worker sin backend. El archivo `.bpmn` estándar es la única fuente de verdad del diagrama y de la documentación por elemento (namespace `lila:` en extensionElements); los parámetros de simulación viven en `scenario.json` aparte, keyed por id BPMN, con vocabulario BPSim 2.0 y herencia `extends` para what-if; el motor es una función pura `simulate(ir, scenario) → RunResult` determinista por semilla que emite tabla de resultados con las mismas columnas que Bizagi más percentiles, colas, throughput, costo por caso, ranking de cuellos de botella y event log por caso. No se adopta ni forkea ningún motor existente (no hay ninguno con licencia permisiva, activo y ejecutable en navegador; Prosimos y Scylla se usan solo como oráculos). Versionado MVP = git y archivos; la plataforma (repositorio, RACI, catálogo, REST, MCP, entrevistas, minería) se añade como paquetes que consumen los mismos tres contratos JSON (IR, escenario, resultados) y el mismo namespace `lila:`, sin tocar el motor. Cinco hitos con pruebas de aceptación ejecutables llevan de `lila run` en consola a una web estática con what-if y un servidor MCP.

## Stack

- **engine_language**: TypeScript estricto, ESM, sin dependencias en runtime en el motor. Versiones verificadas hoy en npm: typescript 7.0.2 (`latest`, Apache-2.0; si el tooling de Vite/vitest tropieza con TS 7 se pina 5.9.x sin cambiar nada más), Node ≥ 22.12 (requisito de vitest 5.0.0; la máquina tiene 24.16.0), pnpm 11.25.0 workspaces, vitest 5.0.0 (MIT) para tests, build con `tsc` (sin bundler en los paquetes; solo Vite para la web). PRNG propio sembrado (mulberry32/xoshiro, ~10 líneas). Justificación: benchmark local verificado de 100.000 casos en 143 ms en JS frente a 1.273 ms en SimPy nativo y 2.798 ms bajo Pyodide, un solo runtime para navegador, CLI, REST, MCP y tests, y ninguna librería DES en TS con adopción real (0–35 estrellas, un autor cada una).
- **editor**: bpmn-js 18.27.1 (licencia bpmn.io = MIT + marca de agua obligatoria y visible; publicada el 2026-09-03, 27 releases en 2026) usado tal cual, sin fork. Alrededor: bpmn-moddle 10.2.0 (MIT, parser/serializador, Node y navegador, preserva namespaces ajenos en round-trip — verificado con archivos reales de Bizagi, Signavio/qbp, jBPM/BPSim), bpmnlint 11.13.0 (MIT, validación en CLI y UI), bpmn-auto-layout 1.3.0 (MIT, para diagramas creados por agentes sin coordenadas), bpmn-js-token-simulation 0.40.0 (MIT) solo como vista de 'validación de rutas' (equivalente al Nivel 1 de Bizagi). Panel de propiedades propio en React (los paquetes oficiales del panel no publican tipos y arrastran camunda-bpmn-js-behaviors). Descartados: KIE bpmn-editor (una sola release, React ≤18, semántica jBPM; revisar en 12 meses), diagram-js solo (reescribir ~28.000 líneas), LogicFlow (no conforme), Camunda Web Modeler (propietario).
- **ui**: React 19.2.8 + Vite 8.2.2, SPA estática sin backend: abre `.bpmn` y `scenario.json` desde disco (input file / File System Access API donde exista), guarda por descarga, borradores en IndexedDB; el motor corre en un Web Worker (mismo bundle de `@lila/sim`). Cubre macOS/Linux/navegador desde el primer despliegue (GitHub Pages o cualquier estático). Tauri opcional después, solo como envoltorio; la marca de agua de bpmn-js debe seguir visible dentro.
- **persistence_mvp**: Sistema de archivos + git. Convención de carpeta por proceso (`processes/<clave>/model.bpmn`, `processes/<clave>/scenarios/<nombre>.json`, `catalog.json` en la raíz del workspace). Versiones AS-IS/TO-BE = commits/tags de git o dos escenarios con `extends`; comparar versiones = diff XML/JSON. En navegador: IndexedDB para borradores, nada más. Sin base de datos, sin Docker, sin servidor.
- **persistence_platform**: Cuando exista el módulo Repositorio (multiusuario): paquete `@lila/repo` con una interfaz de tres operaciones (get/put/list de archivos por clave y versión) y dos implementaciones: filesystem (la del MVP) y SQL. SQLite vía better-sqlite3 13.0.3 (MIT) para self-host de un equipo; PostgreSQL cuando haya concurrencia real. Esquema mínimo: `process_versions(key, version_tag, bpmn_xml, created_at, author)`, `scenarios(process_key, name, json jsonb)`, `runs(id, scenario_ref, result jsonb, event_log blob/parquet)`; las tablas por elemento (actividades, RACI, refs a catálogo) son un índice DERIVADO del XML mediante el mismo parser `@lila/bpmn`, nunca un segundo modelo canónico (patrón Camunda Hub 8.10 / Flowable: 'versión = snapshot de fichero').
- **api_and_mcp**: Las operaciones de dominio son funciones TS puras con esquemas zod 4.5.4 (`validate`, `parse`, `resolveScenario`, `simulate`, `compare`, `patchScenario`, `annotateElement`) definidas en los paquetes `bpmn`/`sim`/`core`. Tres adaptadores finos sobre la misma lista: CLI con commander 15.0.0 (MIT), REST con hono 4.13.5 (MIT, corre en Node/Bun/Workers) y MCP con @modelcontextprotocol/server 2.0.0 (MIT, spec 2026-07-28, transporte stdio primero; ~15 líneas por tool, el mismo esquema zod sirve de inputSchema). El MCP llega en el hito 5 porque es casi gratis; el REST y la persistencia esperan a que haya un segundo usuario.

## Diseño del motor

PIPELINE. `model.bpmn` → `@lila/bpmn.parse()` (bpmn-moddle 10.2.0 → `ProcessIR`) → `@lila/bpmn.lint()` (bpmnlint + reglas propias) → `@lila/core.resolveScenario()` (resuelve `extends` en cadena con deep-merge donde `null` borra, valida con zod, aplica defaults degradantes: sin `resources` ⇒ capacidad infinita, sin `calendar` ⇒ 24×7, gateway XOR sin `probability` ⇒ reparto equitativo, sin `triggerCount` ⇒ parar por `duration`) → `@lila/sim.compile()` (tablas indexadas por entero: nodos, sucesores, pools, calendarios, distribuciones ya instanciadas como closures) → `@lila/sim.run()` (bucle DES) → `RunResult` + event log en streaming. Cada paso es una función pura con entrada y salida JSON; no hay clases `Scheduler` abstractas ni adaptadores a motores ajenos: el contrato es el JSON, y si un día se reescribe el motor en Rust→WASM se respeta `simulate(ir, scenario) → RunResult` y punto.

IR (`ProcessIR`, en `@lila/core`): `{ id, name, nodes: Node[], flows: Flow[], lanes: {id,name,nodeIds}[], source: {exporter, exporterVersion, originalIds} }`; `Node = { id, type: 'start'|'end'|'terminate'|'task'|'xor'|'or'|'and'|'timer', name, lane, subprocessId? }`; `Flow = { id, from, to, name, isDefault }`. Toda variante de tarea (user, service, script, manual…) se aplana a `task`; los subprocesos embebidos se aplanan (su start/end interno se vuelven nodos pass-through y cada nodo conserva `subprocessId` para agregar métricas por subproceso); los reusables/call activities se tratan como una `task` con tiempo global, igual que Bizagi. Ids: se conserva el `id` BPMN tal cual; si no es NCName (Bizagi puede exportar ids que empiezan por dígito y rompen bpmn-js) se sanitiza con un mapa `originalIds` reversible.

SCHEDULER. Heap binario ordenado por `(t, seq)` donde `seq` es un contador monótono: dos eventos al mismo instante siempre salen en orden de inserción, lo que hace el resultado byte-idéntico entre corridas y plataformas. Reloj virtual en segundos desde `run.start` (float64). Un PRNG por replicación derivado de `hash(seed, replicationIndex)`; dentro de la replicación un stream por elemento derivado de `hash(seed, rep, elementId)` (cuesta 5 líneas y da 'common random numbers': añadir una tarea no cambia los números de las demás, lo que hace los what-if mucho más legibles). Nunca `Math.random` ni `Date`. Tipos de evento: `arrive`, `taskStart`, `taskEnd`, `timerEnd`, `calendarOpen`. Complejidad O(E log E); el benchmark local de esta estructura da 2–4 M eventos/s.

TOKENS Y GATEWAYS. Un caso = conjunto de tokens con `caseId`, `replication`, `t0`. XOR: elige flujo saliente por `probability` (el `isDefault` recibe el residuo si las probabilidades no suman 1; lint avisa). AND fork: crea un token por salida. AND join: contador por `(caseId, gatewayId)`; dispara cuando llegan tantos tokens como flujos entrantes. OR (inclusive, hito 5): cada salida se activa con su probabilidad independiente (al menos una; si ninguna, el default), y el join espera a los tokens activos del caso registrados en el fork, que es la semántica práctica de Bizagi/Prosimos (sin análisis de alcanzabilidad). Timer intermedio: retardo `processingTime` sin recurso. End: consume el token; el caso termina cuando tiene cero tokens; `terminate` mata todos los tokens del caso. Casos iniciados y no terminados al cierre cuentan como `started` pero no `completed` (Bizagi hace lo mismo).

RECURSOS. `resources[pool] = { capacity, costPerHour, fixedCost, calendar }`. Una tarea declara `resources: [{ref, quantity}]` con semántica AND (necesita todos; OR alternativo se difiere: no está en el MVP porque exige política de selección que Bizagi no documenta). Cola FIFO por pool con desempate por `seq`; se registra `enabledAt` al llegar al nodo y `startedAt` al conseguir todos los recursos (tomar varios pools se hace atómicamente cuando todos están disponibles, evitando deadlocks por retención parcial). Prioridades, preempción, batching y selección OR quedan como campos reservados en el esquema (`priority`, `selection`) que el motor rechaza con error explícito hasta implementarlos.

CALENDARIOS. `calendars[name].intervals = [{days:[MON..SUN], from:'HH:MM', to:'HH:MM'}]`, patrón semanal relativo a `run.start`, sin DST ni festivos en v1 (campos `holidays` y `timezone` reservados). Se compilan a una función `nextOpen(t)` y `openUntil(t)` con búsqueda en una tabla de 7×intervalos. Semántica documentada en BPMN_PROFILE.md: (a) las llegadas con calendario se desplazan al siguiente instante abierto; (b) el recurso solo se asigna en horario abierto; (c) una tarea en curso al cerrar el turno se PAUSA y reanuda al abrir (procesamiento elástico); el tiempo pausado se contabiliza como `offHoursWait`, separado de `resourceWait`, porque Bizagi no separa ambos y es la queja recurrente de 'poca granularidad'. Es la única parte con complejidad real; por eso está en el modelo de recursos desde el hito 2 aunque se implemente en el 3.

DISTRIBUCIONES (las 13 de BPSim + constante, parámetros NOMBRADOS): `constant{value}`, `uniform{min,max}`, `triangular{min,mode,max}`, `exponential{mean}`, `normal{mean,sd}` (truncada a ≥0, lint avisa si P(x<0)>1 %), `truncatedNormal{mean,sd,min,max}`, `lognormal{mean,sd}` (de la variable, no de su log), `gamma{shape,scale}`, `erlang{k,mean}`, `weibull{shape,scale}`, `beta{alpha,beta,min,max}`, `poisson{mean}`, `binomial{n,p}`, `user{values:[{value,probability}]}`. Muestreo por inversión o Box-Muller/Marsaglia; ~150 líneas, sin dependencias.

EVENT LOG. Filas `{ replication, caseId, elementId, resourceId?, event: 'enabled'|'started'|'completed', t }` (segundos; la CLI las vuelca a CSV con timestamps ISO derivados de `run.start`). Se emite por callback `opts.onEvent` para que la web pueda descartarlo o muestrear cuando hay 30 replicaciones × 10.000 casos; la CLI lo escribe en streaming. Es el formato plano que XES (IEEE 1849) y OCEL 2.0/pm4py consumen tras un mapeo trivial, así que la fase de minería no necesita cambios en el motor.

MÉTRICAS (`RunResult`). Por elemento: `started, completed, processing{min,max,mean,total}, resourceWait{min,max,mean,sd,total}, offHoursWait{...}, queueLength{mean,max}, fixedCostTotal` (las columnas de Bizagi con sus mismos nombres en la CLI, más las extras). Por recurso: `utilization, busyTime, fixedCost, unitCost, totalCost`. Por proceso: `started, completed, cycleTime{min,max,mean,sd,p50,p90,p95}, waitTime{...}, throughputPerHour, costPerCase, totalCost`. `bottlenecks`: ranking por `resourceWait.total` y utilización. Con `replications > 1` cada métrica lleva `mean, sd, ci95` entre replicaciones y el event log es por replicación. `warmup` excluye de las estadísticas los casos iniciados antes; parada = min(`duration`, `triggerCount`), como Bizagi. `compare(a, b)` produce la tabla lado a lado con deltas absolutos y relativos y marca los que superan el CI.

DETERMINISMO Y VALIDACIÓN. Test de oro: misma (IR, escenario, seed) ⇒ `JSON.stringify(result)` idéntico en Node 22, Node 24 y Chrome (worker). Oráculos: (1) M/M/1 y M/M/c con fórmulas de Erlang-C (`examples/mm1`, tolerancia 3 % con 30 replicaciones); (2) el script SimPy ya escrito en el scratchpad (`tools/oracles/des_simpy.py`) para el benchmark de 5 tareas; (3) Scylla headless y Prosimos corridos una vez y sus salidas congeladas como fixtures con tolerancia estadística (solo ejecución; ni una línea de su código entra al repo: Prosimos no tiene licencia y embebe jars propietarios de QBP).

REUTILIZACIÓN. Del corpus y la investigación se reutiliza: el heap+reloj+colas de `scratchpad/bench/des.js` como semilla de `@lila/sim` (es código propio), bpmn-moddle/bpmnlint/bpmn-auto-layout como dependencias, el vocabulario y la lista de secciones de Prosimos y BPSim como referencia del formato. No se forkea nada.

## Formato de escenario

Un archivo JSON por escenario, separado del `.bpmn` (ADR-007), keyed por `id` BPMN bajo un único mapa `elements` (1:1 con `ElementParameters/@elementRef` de BPSim 2.0, y la forma más barata de parchear desde un agente: `elements["Task_Preparar"].processingTime.mean = 400`). Todos los tiempos en segundos, dinero en `run.currency`, distribuciones con parámetros nombrados estilo BPSim (nunca posicionales scipy). Esquema zod en `@lila/core` que genera el JSON Schema publicado en `docs/` y valida en CLI, UI y MCP con el mismo código. Herencia `extends` (equivalente a `inherits` de BPSim): deep-merge sobre el padre, `null` elimina una clave, cadenas permitidas, ciclos rechazados.

`processes/pedido/scenarios/as-is.json`:
{
  "$schema": "https://lila-modeler.org/schema/scenario/1.json",
  "version": 1,
  "name": "AS-IS",
  "description": "Operación actual con 2 cajeros",
  "model": "../model.bpmn",
  "run": {
    "start": "2026-09-07T08:00:00",
    "duration": 2592000,
    "warmup": 0,
    "replications": 30,
    "seed": 42,
    "currency": "MXN"
  },
  "calendars": {
    "oficina": { "intervals": [ { "days": ["MON","TUE","WED","THU","FRI"], "from": "09:00", "to": "18:00" } ] }
  },
  "resources": {
    "cajero":   { "name": "Cajero",   "capacity": 2, "costPerHour": 220, "fixedCost": 0, "calendar": "oficina" },
    "cocinero": { "name": "Cocinero", "capacity": 3, "costPerHour": 180, "calendar": "oficina" }
  },
  "elements": {
    "StartEvent_Pedido": { "interTriggerTimer": { "type": "exponential", "mean": 240 }, "triggerCount": 10000, "calendar": "oficina" },
    "Task_TomarPedido":  { "processingTime": { "type": "triangular", "min": 60, "mode": 120, "max": 300 }, "resources": [ { "ref": "cajero", "quantity": 1 } ], "fixedCost": 2.5 },
    "Task_Preparar":     { "processingTime": { "type": "normal", "mean": 480, "sd": 90 }, "resources": [ { "ref": "cocinero" } ] },
    "Timer_Reposo":      { "processingTime": { "type": "constant", "value": 600 } },
    "Flow_Aprobado":     { "probability": 0.78 },
    "Flow_Rechazado":    { "probability": 0.22 }
  }
}

`processes/pedido/scenarios/to-be-3-cajeros.json`:
{ "version": 1, "name": "TO-BE 3 cajeros", "extends": "as-is.json", "resources": { "cajero": { "capacity": 3 } } }

Reglas: `version` entero en la raíz; claves de `elements` deben existir en el IR (lint: error si falta, warning si sobra); `probability` solo en sequence flows; `interTriggerTimer`/`triggerCount` solo en start events y timers generadores; `processingTime` en tareas y timers; `resources[].quantity` por defecto 1; `run.duration` y `triggerCount` son ambos opcionales pero al menos uno debe existir. Campos reservados que el esquema acepta pero el motor rechaza con mensaje claro hasta que se implementen: `priority`, `selection: "OR"`, `calendars.*.holidays`, `calendars.*.timezone`, `conditions`. Resultados: `RunResult` JSON propio (docs/RESULTS_FORMAT.md) y event log CSV; la CLI vuelca la tabla con los nombres de columna de Bizagi (Name, Type, Instances started/completed, Min/Max/Avg/Total time, Wait min/max/avg/sd/total, Fixed cost; Resources: Utilization, Fixed cost, Unit cost, Total cost) para que un usuario académico migre comparando números. Adaptadores en los bordes, por orden de coste/beneficio: importador `qbp:processSimulationInfo` (hito 5, ~150 líneas, 182 muestras en GitHub, sirve para fixtures y usuarios de Apromore/Simod), exportador a JSON Prosimos (solo para oráculo), import/export BPSim 2.0 como archivo `.bpsim` independiente cuando aparezca un usuario de Sparx EA. No hay importación de escenarios desde Bizagi: su exportación BPMN solo lleva colores (`bizagi:BizagiProperties`), verificado en cinco archivos reales de 2014 a 2026.

## Alcance del MVP

- BPMN soportado (aplanado a IR): start/end event 'none', terminate end, todas las variantes de task como tarea genérica, sequence flow (con default), exclusive gateway con probabilidades por flujo (reparto equitativo si faltan), parallel gateway fork/join, timer intermediate catch event como retardo, subproceso embebido aplanado (hito 5), inclusive gateway con probabilidades independientes (hito 5). Lanes y pools se conservan como metadatos para reportes.
- Escenario JSON v1: run (start, duration, warmup, replications, seed, currency), calendarios semanales, pools de recursos (capacity, costPerHour, fixedCost, calendar), elementos keyed por id (interTriggerTimer, triggerCount, processingTime, resources AND, fixedCost, probability), herencia `extends`, validación con JSON Schema, parada por duración o triggerCount (el primero).
- 14 distribuciones con parámetros nombrados (constante + las 13 de BPSim 2.0, incluida empírica) y PRNG sembrado con streams por elemento.
- Motor determinista: mismo input + seed ⇒ salida idéntica; replicaciones con media/sd/IC95; warm-up; event log en streaming (replication, caseId, elementId, resourceId, event, t).
- Resultados: tabla por elemento, por recurso y por proceso con exactamente las columnas de Bizagi más p50/p90/p95 de ciclo y espera, longitud de cola media/máx, throughput/hora, costo por caso, espera fuera de horario separada de espera por recurso, ranking de cuellos de botella.
- CLI `lila`: `validate model.bpmn`, `run model.bpmn scenario.json [--csv out/] [--json]`, `compare a.json b.json` (lado a lado con deltas y marca de significancia), `import-qbp` (hito 5), `mcp` (hito 5, stdio).
- Web estática (sin backend): editor bpmn-js con extensión `lila`, panel de escenario (recursos, calendarios, por elemento), ejecutar en Web Worker con barra de progreso y cancelación, tabla de resultados, overlay de cuellos de botella sobre el diagrama, comparación de dos escenarios, abrir/guardar archivos, token simulation como vista de validación de rutas.
- Extensión `lila:` v1 dentro del .bpmn solo para documentación: `bpmn:documentation` estándar + `lila:responsibility type=R|A|C|I roleRef`, `lila:systemRef`, `lila:documentRef`, `lila:riskRef`, `lila:controlRef`, `lila:kpiRef`, `lila:input`, `lila:output`, `lila:versionTag`. Referencias a `catalog.json` con ids estables; referencia colgante = warning de lint. En el MVP solo se lee/escribe y se muestra en el panel; RACI matrix y catálogo UI vienen después.
- Oráculos y fixtures: proceso benchmark `examples/pedido`, colas M/M/1 y M/M/c analíticas, script SimPy, salidas congeladas de Scylla/Prosimos con tolerancia estadística.
- FUERA del MVP (con motivo): recursos con selección OR y prioridades (Bizagi no documenta su política), preempción configurable, boundary events, event-based gateway, message/signal events, multi-instancia, choreography/conversation, lectura del .bpm propietario, BPSim export (hasta que haya usuario de Sparx EA), animación con contadores en vivo (token-simulation cubre la parte didáctica), Excel (CSV basta; XLSX es una función después), persistencia en base de datos, REST, autenticación, Docker, Tauri.

## Hitos

### M0 — Esqueleto y contratos (semana 1)

Monorepo pnpm con `packages/{core,bpmn,sim,cli}`, tsconfig estricto, vitest, CI en Node 22 y 24. `@lila/core` con tipos y esquemas zod de ProcessIR, Scenario v1, RunResult, EventLogRow, Catalog; JSON Schema generado a `docs/`; descriptor moddle `lila.json`; generador de ids NCName. `@lila/bpmn.parse()` con bpmn-moddle produciendo IR del benchmark `examples/pedido/model.bpmn` (dibujado en bpmn-js o Camunda Desktop Modeler) y de los .bpmn reales de Bizagi. docs/BPMN_PROFILE.md, SCENARIO_FORMAT.md y RESULTS_FORMAT.md escritos ANTES del motor.

_Aceptación_: `pnpm test` en verde con: (1) parse de examples/pedido produce IR con los nodos/flows esperados (snapshot); (2) parse de los 5 .bpmn de Bizagi del corpus no lanza, conserva `bizagi:` en round-trip y sanitiza ids no-NCName con mapa reversible; (3) `Scenario.parse(as-is.json)` valida y `to-be-3-cajeros.json` resuelve `extends` a un objeto igual al AS-IS salvo capacity=3; (4) escenario con clave inexistente en `elements` produce error con el id y la línea.

### M1 — `lila run` niveles 1–2 de Bizagi (validación + tiempo)

`@lila/sim` con heap, reloj, PRNG por elemento, 14 distribuciones, XOR/AND/timer/start/end/terminate, capacidad infinita, warm-up, replicaciones, parada por duration/triggerCount, event log en streaming, métricas por elemento y proceso. CLI `lila validate` y `lila run` con tabla en consola (columnas Bizagi + percentiles) y `--json`/`--csv`.

_Aceptación_: (1) Determinismo: `lila run pedido as-is --json` dos veces ⇒ archivos byte-idénticos, y el mismo resultado en Node 22 y 24. (2) Proceso lineal con tiempos constantes ⇒ cycle time exactamente la suma (sin espera). (3) XOR 0.78/0.22 con 10.000 casos ⇒ tokens por flujo dentro de ±1.5 % y AND join ⇒ completed == started al cierre. (4) Llegadas exponenciales media 240 s durante 30 días ⇒ started ≈ 10.800 ±2 %. (5) Cada distribución: media y sd muestrales de 100.000 muestras dentro del 2 % de la teórica. (6) 100.000 casos × benchmark corren en < 1 s en Node en la máquina de Brito.

### M2 — Recursos y costos (nivel 3)

Pools con capacidad, colas FIFO con desempate determinista, asignación AND multi-pool atómica, `enabled/started/completed` en el event log, resourceWait min/max/mean/sd/total, queueLength, utilización, costos fijos/unitarios/totales, costo por caso, ranking de cuellos de botella, `lila compare` con deltas y significancia por IC95 entre replicaciones.

_Aceptación_: (1) `examples/mm1`: M/M/1 con ρ=0.8, 30 replicaciones ⇒ espera media dentro del 3 % de ρ/(μ−λ) y utilización 0.80±0.02; M/M/3 dentro del 3 % de Erlang-C. (2) Benchmark de 5 tareas del scratchpad ⇒ avgCT, p95 y utilizaciones por recurso dentro del IC95 de `tools/oracles/des_simpy.py`. (3) Fixture congelado de Scylla para `examples/pedido` reproducido dentro de tolerancia estadística documentada. (4) `lila compare as-is to-be-3-cajeros` marca como significativa la reducción de espera en Task_TomarPedido y como no significativa la de Task_Preparar. (5) Recurso ausente en escenario ⇒ el resultado es idéntico al de M1 (degradación a capacidad infinita).

### M3 — Calendarios (nivel 4) = paridad Bizagi en CLI

Calendarios semanales en llegadas y recursos; pausa/reanudación de tareas al cerrar turno; `offHoursWait` separado; disponibilidad por franja; lint de escenario (probabilidades que no suman 1, normal con masa negativa, calendario sin intervalos). Documento de paridad `docs/BIZAGI_PARITY.md` con el checklist de la investigación marcado.

_Aceptación_: (1) Tarea de 2 h que empieza a las 17:30 con calendario 9–18 ⇒ termina a las 10:30 del día siguiente hábil y registra offHoursWait = 15 h, resourceWait = 0. (2) Llegadas 24×7 con recursos 9–18 L–V ⇒ utilización calculada sobre horas abiertas, no sobre horas de reloj, y cola máxima el lunes 09:00. (3) Escenario sin calendarios ⇒ resultado idéntico al de M2. (4) Los ejemplos de niveles 3 y 4 de help.bizagi.com reproducidos como escenarios; los valores publicados (los que existan) quedan dentro del IC95. (5) 30 replicaciones × 10.000 casos del benchmark con calendarios en < 10 s en Node.

### M4 — Web estática: editar, simular, comparar en navegador

`apps/web`: bpmn-js 18.x con `moddleExtensions: { lila }`, abrir/guardar .bpmn y scenario.json, panel de escenario (recursos, calendarios, por elemento seleccionado, con el JSON Schema como fuente de los formularios), ejecución en Web Worker con progreso y cancelación, tabla de resultados, overlay de cuellos de botella (renderer custom que colorea por resourceWait), comparación de dos escenarios, token-simulation como pestaña de validación, marca de agua bpmn.io visible en la esquina reservada. Despliegue a GitHub Pages.

_Aceptación_: (1) En Chrome y Safari en macOS y en Firefox en Linux: abrir examples/pedido/model.bpmn + as-is.json, correr 30×10.000 en el worker en < 15 s sin congelar la UI, y la tabla coincide byte a byte con `lila run --json` (mismo seed). (2) Crear una tarea ⇒ el nombre queda en edición inmediata sin texto 'Task 1'. (3) Editar `capacity` en el panel, guardar el escenario ⇒ el archivo descargado es válido contra el JSON Schema y `lila run` lo acepta. (4) Añadir `lila:responsibility` desde el panel ⇒ aparece en el XML exportado y sobrevive a abrir/guardar en Camunda Desktop Modeler. (5) El BPMN más grande que tenga Brito importa y se mueve sin bloqueos > 1 s.

### M5 — Cobertura BPMN ampliada, importador qbp y MCP

Subproceso embebido aplanado con métricas agregadas, inclusive gateway, `lila import-qbp` (BPMN con `qbp:processSimulationInfo` → model.bpmn + scenario.json), `@lila/mcp` con tools `validate_bpmn`, `run_simulation`, `compare_scenarios`, `patch_scenario` (JSON Patch sobre el escenario), `get_element`, `annotate_element` (escribe `lila:*`), `create_process_draft` (IR mínimo → .bpmn con bpmn-auto-layout). Servido por `lila mcp` (stdio).

_Aceptación_: (1) Los .bpmn con qbp del repo de Prosimos (financial.bpmn) importan y `lila run` produce métricas dentro del IC95 del fixture de Prosimos. (2) Subproceso embebido con AND interno ⇒ mismas métricas que el proceso equivalente aplanado a mano. (3) Desde Claude Code con el MCP configurado: 'simula qué pasa con un cajero más' ⇒ el agente llama patch_scenario + run_simulation + compare_scenarios y la respuesta cita el delta de espera; el escenario resultante queda en disco y es válido. (4) Un agente crea un proceso de 6 nodos vía create_process_draft ⇒ el .bpmn abre en bpmn-js con layout legible y `lila validate` sin errores.

## Evolución a plataforma

La regla de enganche es una sola: cada módulo nuevo consume los contratos de `@lila/core` (ProcessIR, Scenario, RunResult, EventLogRow, Catalog, descriptor `lila`) y las funciones puras de `@lila/bpmn` y `@lila/sim`; ninguno modifica el motor ni introduce un segundo modelo canónico del proceso. El archivo `.bpmn` sigue siendo la verdad del diagrama y de la documentación por elemento; los sidecars JSON (escenarios, catálogo, resultados) siguen siendo keyed por id BPMN.

Repositorio y versiones (módulo #2): `@lila/repo` con interfaz de tres operaciones (`getVersion(key, tag)`, `putVersion(key, bpmnXml, meta)`, `list()`) y las mismas para escenarios y runs. Implementación 1 = la carpeta `processes/<clave>/` + git (ya existe en el MVP); implementación 2 = SQLite/Postgres guardando el XML como blob por `(key, versionTag)` y escenarios/resultados en jsonb, con tablas por elemento derivadas al guardar mediante `@lila/bpmn.parse()` (índice, no modelo). AS-IS/TO-BE = dos versiones con `lila:versionTag` en el `bpmn:process` (calcado de `zeebe:versionTag`) o dos escenarios con `extends`; comparar = diff XML + `compare()` de resultados, como hace Camunda Hub 8.10. Flujo de liberación tipo ADONIS (Draft/Review/Released/Valid until) = columnas de estado sobre la fila de versión, sin tocar archivos.

Catálogo, RACI, sistemas, documentos, riesgos, controles, KPIs (módulo #3): `catalog.json` (después tabla `catalog_items(id, type, name, attrs jsonb)`) con ids estables y tipos; los elementos apuntan con `lila:*Ref`; la matriz RACI es una consulta sobre el IR (`nodes × responsibilities`) y 'actividades sin responsable' es una regla de lint. Patrón Signavio dictionary / ADONIS repository objects / ARIS definición-ocurrencia, sin reinventar: el elemento referencia, nunca contiene texto libre. Los atributos custom por tipo de elemento se añaden al descriptor `lila` v1.x de forma aditiva; bpmn-moddle conserva lo que no conoce.

REST y MCP (módulos #4 y #5): la lista de operaciones ya existe como funciones con esquemas zod; `packages/api` (hono) las expone como `POST /processes/:key/versions/:tag/simulate` etc. y `@lila/mcp` como tools. Permisos (`process:read`, `simulation:run`…) son un middleware sobre esa misma lista cuando haya usuarios; hasta entonces, no existen. La spec MCP 2026-07-28 es request/response sin sesión, lo que encaja con funciones puras.

Agentes de entrevista y asistencia (módulos #6–#7): un agente produce IR o parches (`create_process_draft`, `patch_scenario`, `annotate_element`) a través del MCP; `bpmn-auto-layout` genera el DI; `bpmnlint` + reglas `lila` devuelven los findings (contradicciones, faltantes) como datos estructurados. Los hallazgos (`Finding`, `Interview`) son documentos JSON en `processes/<clave>/findings/` y luego filas; no tocan el motor.

Process mining (módulo #8): proceso Python separado (`mining/`, pm4py AGPL-3.0 aislado por licencia) que consume el event log CSV/XES del motor o logs reales, y produce un `scenario.json` AS-IS observado (lo que hace Simod para Prosimos) y un `RunResult`-compatible con métricas reales para comparar 'documentado vs observado' con el mismo `compare()`. Acoplamiento solo por archivos; OCEL 2.0 cuando haga falta.

Lo que NO cambia nunca por estos módulos: el `id` BPMN como clave, el namespace `lila` (solo crece), la forma de `Scenario` v1 (los campos reservados se activan, no se renombran), la firma `simulate(ir, scenario) → RunResult` y las columnas del event log. Lo que puede cambiar libremente: framework web, base de datos, transporte del MCP, editor (si un día KIE madura, se reescribe la UI, no el dominio).

## Decisiones

- **Lenguaje y kernel del motor** → TypeScript con bucle de eventos propio (~300–500 líneas), cero dependencias; ni SimPy/Pyodide, ni Rust/WASM, ni ninguna librería DES en TS.
  - _Por qué_: Benchmark verificado en la máquina de Brito: 100k casos en 143 ms en JS vs 1.273 ms SimPy nativo y 2.798 ms SimPy en Pyodide (+~12 MB de runtime y ~1 s de arranque). Un solo runtime cubre navegador (worker), CLI, REST, MCP y tests. Las librerías DES en TS tienen 0–35 estrellas y un autor; los crates Rust no traen primitivas de recursos y el toolchain wasm acaba de reorganizarse. Los contratos JSON permiten reimplementar el kernel en Rust después si alguna vez hiciera falta.
- **Motor existente: usar, envolver, forkear o reemplazar** → Reemplazar (escribir propio). Prosimos y Scylla solo como oráculos numéricos ejecutados una vez; bpmn-js-token-simulation solo como vista didáctica.
  - _Por qué_: Prosimos no tiene LICENSE (todos los derechos reservados), embebe jars propietarios de QBP, exige Python <3.12 con polars/pyarrow y su main está parado desde 2025-01; Scylla es MIT pero Java+Swing+DESMO-J 2017; BIMP/QBP es cerrado; Apromore archivado 2025-08; bpmn-engine/Camunda/SpiffWorkflow son motores de ejecución con licencias inadecuadas (Camunda License, LGPL). Ninguno corre en navegador.
- **Editor BPMN** → bpmn-js 18.27.1 tal cual, con la marca de agua bpmn.io visible en la esquina reservada del canvas; panel de propiedades propio en React.
  - _Por qué_: Es la única librería del sector con releases mensuales en 2026, tipos incluidos y ejemplos oficiales para moddle extension, properties provider y renderer custom; el comportamiento 'nueva tarea → edición inmediata sin Task 1' viene de serie. La marca de agua no se puede quitar ni con fork ni con licencia propia (Camunda Desktop Modeler, Fluxnova y Miragon la llevan); reemplazarla por diagram-js son ~28.000 líneas. Los paquetes oficiales del properties panel no publican tipos y arrastran dependencias Camunda, por eso el panel es propio.
- **Identidad de elemento** → El atributo `id` BPMN, NCName, generado por Lila con prefijo por tipo y sufijo aleatorio (`Task_7f3k2q1`), nunca regenerado al importar/exportar/renombrar, nuevo id al copiar. Ids ajenos no-NCName se sanitizan con mapa reversible.
  - _Por qué_: Es la única clave que comparten todas las herramientas (Signavio `sid-uuid`, bpmn-js `Activity_x`, jBPM `_uuid`) y de la que cuelgan BPSim, qbp, Prosimos y Scylla. Usar nombres como clave es la decisión que fuerza reescrituras. bpmn-js falla con ids que empiezan por dígito.
- **Identidad y versión de proceso** → `bpmn:process@id` como clave lógica (slug ASCII, sin acentos) + `lila:versionTag`; `exporter="Lila Modeler"` y `exporterVersion` en definitions; en disco `processes/<clave>/`.
  - _Por qué_: Patrón común de Flowable (definition key + version), Bonita (pool name + version) y Camunda (process id + versionTag). Hace que la futura tabla `process_versions(key, tag)` sea un espejo del sistema de archivos, no una migración.
- **Dónde vive cada dato** → Diagrama y documentación por elemento dentro del .bpmn (`bpmn:documentation` + `lila:` extensionElements); parámetros de simulación en `scenario.json` aparte; catálogo en `catalog.json`; resultados en JSON + CSV.
  - _Por qué_: La documentación viaja con el archivo y sobrevive a otras herramientas (bpmn-moddle preserva namespaces desconocidos, verificado); los escenarios fuera del XML permiten N escenarios por diagrama, diffs de git sin ruido de coordenadas DI y parches triviales desde MCP. Confirma ADR-001 y ADR-007 y reinterpreta 'Internal model ≠ BPMN XML': la base de datos será un índice derivado, no un segundo modelo.
- **Namespace de extensión** → Uno solo, `xmlns:lila="https://lila-modeler.org/schema/bpmn/1"`, definido una vez como descriptor moddle JSON en `@lila/core` y compartido por editor, CLI y servidor; elementos (no atributos) para permitir listas; crece de forma aditiva.
  - _Por qué_: Un descriptor compartido evita dos definiciones que divergen; los elementos con `*Ref` a ids de catálogo replican lo que hacen ADONIS/Signavio/ARIS. Riesgo a verificar en M4: que Camunda Desktop Modeler, Signavio y ADONIS conserven `lila:` en round-trip; si alguno lo descarta, el respaldo es `annotations.json` keyed por id con el mismo descriptor.
- **Formato de escenario** → JSON propio v1 con vocabulario BPSim 2.0 (interTriggerTimer, triggerCount, processingTime, probability, quantity, fixedCost/unitCost, seed, warmup, replications), segundos, distribuciones nombradas, un mapa `elements` por id, `extends` para what-if, JSON Schema desde zod. BPSim y qbp solo como adaptadores en los bordes.
  - _Por qué_: Cumple los cuatro criterios (N escenarios, git-friendly, parcheable por agentes, migrable a jsonb sin cambios). BPSim está congelado desde 2016 sin tooling OSS y mezcla layout con parámetros si se embebe; qbp solo admite un escenario y un recurso por tarea; Prosimos usa parámetros posicionales scipy. Bizagi no exporta parámetros, así que la compatibilidad de escenario con Bizagi no existe para nadie.
- **Semántica de calendarios** → Patrón semanal relativo a `run.start`, sin DST/festivos en v1; tareas en curso se pausan al cerrar y reanudan al abrir; espera fuera de horario (`offHoursWait`) separada de espera por recurso; utilización sobre horas abiertas.
  - _Por qué_: Bizagi no documenta qué hace con tareas en curso al cerrar turno ni separa las esperas; elegir una semántica explícita y documentarla en BPMN_PROFILE.md vale más que adivinar la suya, y la separación responde a la queja de 'poca granularidad'. DST y festivos quedan como campos reservados.
- **Determinismo** → Heap con desempate por secuencia, PRNG por elemento derivado de (seed, replicación, id), sin Math.random/Date; test de igualdad byte a byte entre Node 22, Node 24 y navegador.
  - _Por qué_: Reproducibilidad es requisito académico y de tests; streams por elemento dan common random numbers para que los what-if no cambien los números de elementos no tocados. Prosimos ni siquiera expone seed.
- **Estructura de paquetes** → Cuatro paquetes en el MVP (`core`, `bpmn`, `sim`, `cli`) + `apps/web`; `mcp` en M5; `repo`, `api`, `catalog`, `interview`, `mining` no existen hasta que se necesiten.
  - _Por qué_: Fewest moving parts: `core` es tipos+zod (barato) pero es el único lugar donde viven los contratos que los módulos futuros consumen; separar `sim` de `bpmn` mantiene el motor con cero dependencias y ejecutable en worker. No hay capa de 'domain services' abstracta: las funciones exportadas son los servicios.
- **Versionado y persistencia del MVP** → Archivos + git; en navegador IndexedDB para borradores. Nada de Postgres, Docker, REST ni WebSocket hasta que exista un segundo usuario concurrente.
  - _Por qué_: Regla de Brito: sin infra antes de tiempo. El layout `processes/<clave>/` ya es la forma de la futura tabla de versiones, y `git diff` ya es 'comparar versiones' (Camunda hace diff XML).
- **MCP antes que REST** → `lila mcp` (stdio, @modelcontextprotocol/server 2.0.0) en M5; REST con hono cuando haya repositorio multiusuario.
  - _Por qué_: Brito trabaja con agentes; el MCP sobre funciones puras cuesta ~15 líneas por tool y da valor inmediato ('simula con un cajero más'). REST sin persistencia compartida no aporta nada todavía.
- **Licencias** → Núcleo y UI bajo MIT o Apache-2.0 (decidir en ADR); prohibido AGPL/LGPL/Camunda License en dependencias del núcleo (pm4py, SpiffWorkflow, Camunda 8); Prosimos y jars de QBP jamás en el repo; la marca de agua bpmn.io aceptada.
  - _Por qué_: pm4py es AGPL-3.0 desde 2.7.12 y contaminaría un servicio de red; Prosimos carece de licencia; el jar QBP es propietario. El mining vivirá en un proceso Python aparte acoplado por archivos.
- **Excel, animación y niveles de Bizagi** → No reproducir los '4 niveles' como concepto de producto (el motor degrada: sin recursos ⇒ infinito, sin calendario ⇒ 24×7); CSV en vez de XLSX; token-simulation en vez de animación con contadores.
  - _Por qué_: Los niveles solo describen qué parámetros están rellenos. CSV lo abre Excel y lo consume pm4py; XLSX es una función de 30 líneas después. La animación DES en vivo es cara y no aparece entre las peticiones de usuarios.

## Riesgos

- Semántica de calendarios (pausa/reanudación, utilización sobre horas abiertas) y de inclusive gateway elegida sin poder contrastarla con Bizagi (no documenta la suya y su foro está en mantenimiento): los números diferirán de Bizagi en escenarios de nivel 4. Mitigación: documentar la semántica, ofrecer flag `calendar.taskPolicy` más adelante, y reproducir los ejemplos publicados del help como fixtures.
- Round-trip del namespace `lila:` en herramientas ajenas (Camunda Desktop Modeler, Signavio, ADONIS) no verificado; bpmn-moddle lo conserva pero otros pueden descartarlo (issue histórico bpmn-js #1310). Mitigación: prueba en M4 y respaldo `annotations.json` keyed por id con el mismo descriptor.
- Importación de .bpmn de Bizagi: ids no-NCName, namespace `bizagi` declarado dentro de cada extensionElements (rompió bpmn-js en el pasado, corregido en bpmn-moddle) y pérdida segura de sus extended attributes. Mitigación: fixtures reales en `examples/bizagi-export/` desde M0 y sanitizado de ids con mapa reversible.
- Bus factor 1 (Brito) sobre un motor propio: sin oráculos automatizados el motor puede dar números plausibles pero incorrectos. Mitigación: M/M/1 y M/M/c analíticos y SimPy como tests de CI desde M2; las salidas de Scylla/Prosimos congeladas como fixtures.
- Deriva de alcance hacia la plataforma antes de que el simulador sea confiable. Mitigación: regla del corpus mantenida — nada de repo/RACI/UI de catálogo antes de M3; los contratos de `core` son lo único que se diseña 'para el futuro'.
- TypeScript 7.0.2 (`latest` hoy) es reciente; Vite 8 / vitest 5 / zod 4 pueden tener aristas con él. Mitigación: pinar TS 5.9.x si aparece fricción; nada del diseño depende de TS 7.
- Marca de agua de bpmn-js: aceptada, pero un cambio futuro de licencia por parte de Camunda (como hicieron con Camunda 8) dejaría a Lila con una UI difícil de sustituir. Mitigación: todo lo que importa vive en el .bpmn estándar y en `@lila/bpmn` (Node, sin editor); KIE bpmn-editor es la salida si madura.
- Memoria en navegador con event log de 30 replicaciones × 10.000 casos × ~20 eventos: 6 M filas no caben cómodamente. Mitigación: el log se emite por callback y la web solo agrega o muestrea; el CSV completo solo desde CLI.
- Pyodide/Python descartados pero el público académico puede pedir `import lila` en Python. Mitigación: cliente Python fino sobre la CLI/REST (subprocess + JSON), no bindings.
- MCP SDK v2 (2.0.0, julio 2026) y spec 2026-07-28 son muy recientes; los clientes pueden ir por detrás. Mitigación: stdio primero y tools mínimos; el SDK 1.x sigue con soporte ≥ 6 meses si hay que bajar.
- Uso de Prosimos/Scylla como oráculos: Prosimos sin licencia y con jars propietarios; ejecutarlos localmente para congelar fixtures es defendible, redistribuirlos no. Mitigación: `tools/oracles` documenta cómo generar fixtures sin incluir binarios; el jar QBP nunca entra al repo.
- Nombre 'Lila Modeler' y dominio `lila-modeler.org` usados en el namespace sin verificar disponibilidad de marca/dominio. Mitigación: el URI del namespace puede ser cualquier IRI estable; decidirlo en el ADR de nombre antes de M4 porque cambiarlo después sí duele.
