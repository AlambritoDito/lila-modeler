# Representación e intercambio de los parámetros de simulación (el "escenario"): BPSim 2.0 vs qbp/BIMP embebido vs Prosimos JSON vs Bizagi/Signavio/Camunda, y cómo round-tripea bpmn-moddle. Recomendación para Lila Modeler: JSON de escenario separado del .bpmn, con adaptadores de importación/exportación.

_Investigación verificada el 2026-09-03 por un agente con búsqueda web. Cada hallazgo lleva su nivel de confianza._

## Recomendación

Recomendación: el escenario es un documento JSON propio, pequeño y versionado, separado del .bpmn (confirma ADR-007), un archivo por escenario junto al diagrama (p. ej. `pedido.bpmn`, `pedido.as-is.scenario.json`, `pedido.to-be-2-analistas.scenario.json`) y referenciando a los elementos BPMN por su `id`. Es la opción más barata y la única que cumple a la vez los cuatro criterios: N escenarios por diagrama sin tocar el XML; diffs de git legibles y sin ruido de coordenadas DI; edición por agentes/MCP como JSON-patch sobre mapas por id (`tasks["Task_1"].duration.mode = 400`); y no fuerza reescritura para la plataforma, porque `SimulationScenario` en Postgres será exactamente ese JSON en una columna `jsonb` con `process_version_id` y el runner de hoy (`process-sim run process.bpmn scenario.json`) sigue siendo la misma firma cuando lo llame REST o el MCP. Principios del formato: (1) `version` semántica en la raíz y un JSON Schema desde el día uno (validación en CLI, UI y MCP con el mismo archivo); (2) todos los tiempos en segundos y las distribuciones con parámetros NOMBRADOS y nombres BPSim-like (`normal{mean,sd}`, `triangular{min,mode,max}`, `exponential{mean}`, `uniform{min,max}`, `lognormal`, `gamma`, `constant`), nunca posicionales al estilo scipy; (3) calendarios como intervalos semanales (como qbp/Prosimos), no iCalendar; (4) recursos como pools con `capacity`, `cost_per_hour`, `calendar`, y las tareas apuntan a un pool (una lista de pools deja abierta la puerta a recursos diferenciados/batching estilo Prosimos sin romper el esquema); (5) un campo opcional `extends` para heredar de otro escenario (equivalente a `inherits` de BPSim) que resuelve TO-BE como delta del AS-IS; (6) el .bpmn se mantiene intacto: no se escribe nada dentro, pero bpmn-moddle ya conserva por defecto los bloques ajenos (`bpsim:`, `qbp:`, `bizagi:`), así que un archivo que venga con datos de otra herramienta no se degrada al editarlo.

La interoperabilidad se hace con adaptadores en los bordes, no eligiendo un formato ajeno como canónico. Orden sugerido por coste/beneficio: (a) importador `qbp:processSimulationInfo` → scenario.json (unas 150 líneas: es un XML plano, con XSD público y 182 muestras en GitHub; da fixtures reales para validar el motor contra BIMP/Prosimos y cubre a usuarios de Apromore/Simod); (b) exportador a JSON Prosimos, útil sobre todo como oráculo de pruebas cruzadas del motor (ojo: Prosimos no tiene licencia, se usa solo como referencia, no como dependencia); (c) importar/exportar BPSim 2.0 solo cuando aparezca un usuario con archivos de Sparx EA o cuando convenga decir "compatible con BPSim": el XSD y los ejemplos de la Implementer's Guide son suficientes para escribirlo en un día, y como BPSim admite archivo independiente (`*.bpsim`) ni siquiera obliga a tocar el .bpmn. No invertir en compatibilidad con Bizagi a nivel de escenario: su exportación BPMN no lleva simulación, así que "importar de Bizagi" es importar el diagrama y capturar parámetros de nuevo (idealmente con el agente de entrevistas), salvo que un spike de una hora demuestre que el ZIP `.bpm` contiene un XML de escenarios parseable. Descartar embeber el escenario en `extensionElements` como modelo interno; si algún día se necesita "un solo archivo" para compartir, se genera un bundle de exportación que inyecta `<lila:scenario>` con el mismo JSON, sin cambiar el modelo.

Ejemplo mínimo (`pedido.as-is.scenario.json`): {"version":"0.1","name":"AS-IS","bpmn":"pedido.bpmn","extends":null,"run":{"cases":10000,"seed":42,"start":"2026-09-07T08:00:00-06:00","warmup_s":3600,"replications":1,"currency":"MXN"},"calendars":{"oficina":[{"from":"MON","to":"FRI","start":"09:00","end":"18:00"}]},"arrivals":{"distribution":{"type":"exponential","mean":240},"calendar":"oficina"},"resources":{"cajero":{"capacity":2,"cost_per_hour":220,"calendar":"oficina"},"cocinero":{"capacity":3,"cost_per_hour":180,"calendar":"oficina"}},"tasks":{"Task_TomarPedido":{"duration":{"type":"triangular","min":60,"mode":120,"max":300},"resource":"cajero","fixed_cost":0},"Task_Preparar":{"duration":{"type":"normal","mean":480,"sd":90},"resource":"cocinero"}},"gateways":{"Gateway_Aprobado":{"Flow_Si":0.78,"Flow_No":0.22}}}. Un TO-BE es `{"version":"0.1","name":"TO-BE +1 cajero","extends":"pedido.as-is.scenario.json","resources":{"cajero":{"capacity":3}}}`. La tabla de mapeo campo↔BPSim↔qbp (p. ej. `tasks[id].duration` ↔ `bpsim:ProcessingTime` ↔ `qbp:durationDistribution`; `gateways[id][flow]` ↔ `bpsim:Probability` en el sequenceFlow ↔ `qbp:sequenceFlow/@executionProbability`; `resources[pool].capacity` ↔ `bpsim:Quantity` ↔ `qbp:resource/@totalAmount`) debería vivir en docs/SCENARIO_FORMAT.md junto al JSON Schema.

Consta de un meta-modelo UML y un formato de intercambio XML definido por XSD (namespace http://www.bpsim.org/schemas/2.0). Existe además BPSim 1.0 (WFMC-BPSWG-2012-01, 2012).

- **[verified]** BPSim está de facto congelado: bpsim.org no muestra ninguna fecha posterior a enero de 2016 ni noticias; el repositorio GitHub del grupo de trabajo (BusinessProcessSimulation/BPSim) tuvo su último push el 2016-12-22; no existe ninguna versión 2.1/3.0.

- **[verified]** Estructura BPSim 2.0: BPSimData contiene 1..* Scenario. Scenario tiene id (xs:ID), name, description, author, vendor, version, created, modified, inherits (IDREF a otro escenario: herencia/override), result (IDREF: escenario de resultados que referencia al de entrada), ScenarioParameters (Start, Duration, Warmup, replication, seed, baseTimeUnit default 'min', baseCurrencyUnit default 'USD', baseResultFrequency, traceOutput/traceFormat default XES), 0..* ElementParameters (elementRef = id del elemento BPMN) con perspectivas TimeParameters (TransferTime, QueueTime, WaitTime, SetUpTime, ProcessingTime, ValidationTime, ReworkTime, LagTime, Duration, ElapsedTime), ControlParameters (Probability, Condition, InterTriggerTimer, TriggerCount), ResourceParameters (Selection, Availability, Quantity, Role), PriorityParameters (Interruptible, Priority), CostParameters (FixedCost, UnitCost), PropertyParameters (Property, QueueLength); Calendar (texto iCalendar RFC 5545 dentro del elemento); VendorExtension. Valores: ConstantParameter, StringParameter, NumericParameter, FloatingParameter, BooleanParameter, DurationParameter (ISO 8601), DateTimeParameter, EnumParameter, ExpressionParameter (string XPath-like con funciones bpsim:getProperty/getResource...), y distribuciones Beta, Binomial, Erlang, Gamma, LogNormal, NegativeExponential, Normal, Poisson, Triangular, TruncatedNormal, Uniform, Weibull, UserDistribution. Los recursos se declaran con el elemento estándar BPMN <resource>.
  - _Evidencia_: XSD BPSim-2.0.xsd (líneas 3-147 y substitutionGroup ParameterValue); spec secciones 6.1-6.4 y 7.1; sección 6.3 'Resources are defined in the BPMN interchange using the <resource> element'.

- **[verified]** Crítica académica (Laue & Müller, ECMS 2016, 'The Business Process Simulation Standard (BPSIM): Chances and Limits'): BPSim funciona bien para escenarios simples y es útil como formato independiente de herramientas, pero (a) las herramientas implementan subconjuntos y añaden extensiones propietarias (Trisotech no permitía asignar recursos a tareas sin editar el XML a mano), (b) los parámetros de distribución son atributos numéricos y no pueden ser expresiones, (c) no hay timers reseteables ni relación con eventos de frontera, (d) el modelo de recursos está poco elaborado: sin semántica definida para prioridad, sin disciplinas de cola (FIFO/LIFO/aleatoria), sin recursos consumibles, sin propiedades definidas por el usuario en recursos, (e) los tipos de resultado son limitados.

Editabilidad por agente/MCP: JSON plano con mapas por id es lo más barato de parchear; BPSim exige navegar substitutionGroups, IDREF y expresiones string. Importar de Bizagi: ninguno lo resuelve (Bizagi no exporta simulación). Interoperabilidad real: qbp tiene el mayor corpus y herramientas vivas (Prosimos, Simod, Apromore); BPSim tiene Sparx EA y L-Sim comerciales, tooling OSS casi nulo.
  - _Evidencia_: Síntesis de los hallazgos anteriores (XSD BPSim, XSD QBP, README Prosimos, ayuda Bizagi, prueba round-trip).
- **[verified]** Los tres formatos comparten el mismo esqueleto conceptual, lo que hace trivial un adaptador: {run: casos/duración/warmup/seed/replicaciones/moneda/unidad}, {arrivals: distribución + calendario}, {resources: pool → capacidad, coste/hora, calendario}, {tasks: id → duración (distribución) + recurso(s)}, {flows/gateways: id → probabilidad}, {calendars: intervalos semanales}. Diferencias menores: BPSim usa ISO 8601 (PT5M) e iCalendar; qbp y Prosimos usan segundos y reglas semanales; Prosimos parametriza distribuciones al estilo scipy (posicional: loc/scale), BPSim y qbp con nombres (mean/standardDeviation, min/mode/max).
  - _Evidencia_: XSD BPSim (TimeParameters/ControlParameters/ResourceParameters/CostParameters, Calendar iCalendar), XSD QBP (DistributionInfo en segundos, TimeTableRule), README Prosimos ('The unit of measurement … is seconds', 'Scipy Stats').

## Preguntas abiertas

- ¿El ZIP .bpm de Bizagi contiene un XML de escenarios parseable? Un spike de una hora con un .bpm real (renombrar a .zip, listar archivos, buscar 'Scenario'/'Simulation') decide si vale la pena un importador Bizagi a nivel de parámetros; hoy la evidencia dice que la exportación BPMN no los lleva.
- ¿La exportación BPMN 2.0 XML de SAP Signavio incluye datos de simulación en algún extensionElement signavio:? No pude abrir la documentación; se necesita un archivo exportado real para confirmarlo.
- ¿Hay usuarios objetivo con Sparx Enterprise Architect? Es el único ecosistema vivo donde importar/exportar BPSim 2.0 aporta valor real; si no los hay, BPSim puede quedarse como exportador opcional de bajo esfuerzo.
- ¿Se adopta compatibilidad de nombres de parámetros con Prosimos (scipy: loc/scale posicionales) o se mantiene la convención nombrada tipo BPSim/qbp y se traduce en el adaptador? Recomiendo nombrada + adaptador, pero conviene decidirlo antes de escribir el JSON Schema.
- ¿Cómo se representan los resultados? BPSim también define un escenario de resultados (ResultRequest/result). Propuesta: JSON de resultados propio + event log CSV/XES; exportar resultados BPSim solo si aparece un consumidor.
- ¿Se admite desde el inicio una lista de pools por tarea (recursos diferenciados, estilo Prosimos) o solo un pool por tarea (estilo qbp/Bizagi)? Impacta el motor más que el formato; el esquema puede aceptar string o array para no cerrar la puerta.
- ¿Qué pasa con expresiones y atributos de caso (branch_rules de Prosimos, ExpressionParameter de BPSim)? Sugerencia: fuera del v0.1 del formato; dejar un campo reservado `conditions` sin implementar.
- Licencia del jar de QBP: no redistribuir; verificar términos con la Universidad de Tartu antes de usarlo siquiera como oráculo en CI.
