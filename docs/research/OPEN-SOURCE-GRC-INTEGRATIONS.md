# Open-source GRC and execution integrations: research for Lila Modeler

> Read this in: [Español](../es/research/OPEN-SOURCE-GRC-INTEGRATIONS.md).

**Review date:** 2026-09-26. **Status:** research and design input, not an implementation or a claim of vendor parity. The [roadmap](../ROADMAP.md) puts risk and controls in phase 4, governance in phase 7, and external execution adapters in phase 8. Its phases 1–2 repository and relationship contracts are prerequisites. The [license decision](../DECISIONS.md#adr-020--licenses) forbids AGPL, LGPL and Camunda License code in `packages/*`. Studying a product, exchanging data with a separately operated service, and reusing its code are three different decisions. A separate process does not by itself settle license obligations; review the exact distribution and deployment before any integration ships.

## Recommendation and evidence limits

Use **CISO Assistant Community** as the first *cybersecurity GRC* reference and the first candidate for a later, opt-in external adapter. Its public model connects assets, scenarios, applied controls, requirements, evidence and audits; its Community edition and REST API are explicitly identified by the vendor. Do **not** import its AGPL code into Lila. Do not copy its user interface or assume its Pro features are available in Community. [Repository and license](https://github.com/intuitem/ciso-assistant-community), [edition comparison](https://intuitem.com/compare), [API](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/integrations/api.md).

Design Lila's own risk catalog for **general operational risk** as well as cyber risk. An interrupted supplier delivery, production bottleneck or safety incident can affect a process without being an information-security threat. Eramba documents asset, third-party and **business** risks, including process and business-unit context, which makes it a useful conceptual cross-check; its current application's reusable OSS license is **unverified**, so it is not a code source. [Eramba risk guide](https://www.eramba.org/learning/courses/79), [vendor edition page](https://www.eramba.org/eramba-software), [vendor forum on private source repository](https://discussions.eramba.org/t/question-cant-access-the-github-repo/4673).

Keep **simulation, GRC assessment, and execution** distinct. Lila simulates scenarios; it does not prove a control operates or execute a BPMN workflow. Flowable Open Source is an Apache-2.0 BPMN/DMN execution candidate with REST APIs, but it requires a later adapter spike and real round-trip fixtures. No workflow engine is selected or embedded here. [Flowable license](https://github.com/flowable/flowable-engine/blob/main/LICENSE), [open-source API documentation](https://www.flowable.com/open-source/docs/), [BPMN REST example](https://www.flowable.com/open-source/docs/bpmn/ch02-GettingStarted).

## Domain findings for Lila's phase-4 contract

| Domain concern | Verified reference behavior | Lila design implication / status |
| --- | --- | --- |
| Context, assets and process links | CISO Assistant [risk scenarios](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/concepts/risk-assessments.md) can connect to assets, threats and controls. Eramba's [guide](https://www.eramba.org/learning/courses/79) ties business risk to a process/business unit as well as asset/third-party contexts. | **Proposed:** one risk identity with a category or taxonomy and typed links to process, BPMN element, asset, organizational unit, supplier and product. Keep those links in Lila's relation index; a cybersecurity threat is optional for a general operational risk. Do not key by display name. |
| Inherent, current and residual | CISO Assistant distinguishes uncontrolled **inherent**, today's **current**, and post-plan **residual** risk; each has probability, impact and level, with consistency checks. [Risk docs](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/concepts/risk-assessments.md). Eramba exposes configurable inherent/residual scoring for its risk types. [Guide](https://www.eramba.org/learning/courses/79). | **Proposed:** version the assessment method and scale; store raw probability/impact, evaluated level, assessor, date and rationale for each state. Define whether “residual” means present after effective controls or a target after planned treatments in a separate phase-4 ADR. Never silently equate the two vendor meanings. Missing is not zero. |
| Scales and heatmaps | CISO Assistant supports configurable imported matrices; changing a matrix clamps values rather than proportionally rescaling them. [Risk docs](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/concepts/risk-assessments.md). Eramba documents classification, addition/multiplication and labeled matrix cells. [Guide](https://www.eramba.org/learning/courses/79). | **Proposed:** immutable scale revision in each recorded assessment, explicit calculation rule and label/color mapping; recomputation requires reviewed migration. A heatmap cell should drill down to assessments and show unrated risks separately. |
| Controls, effectiveness and treatments | CISO Assistant [applied controls](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/concepts/applied-controls.md) can satisfy many requirements, mitigate risk scenarios and have evidence; active/degraded status is distinct from planned. SimpleRisk describes [control test results](https://support.simplerisk.com/kb/02-07-control-tests-and-evidence-collection) and a mitigation estimate that changes residual risk. | **Proposed:** separate control definition, deployment/occurrence, owner, implementation status, assessment of design/operating effectiveness, test result and treatment action. Do not lower risk automatically because a control link exists or a mitigation percentage was entered. Record the justification and reviewer of any change. |
| Requirements, audit and evidence | CISO Assistant [audits](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/concepts/audits.md) create a requirement assessment per assessable framework item and link reused controls/evidence. Its [evidence](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/concepts/evidence.md) has stable identity, dated/expiring revisions, files or links and SHA-256 hashes. SimpleRisk [tests and evidence](https://support.simplerisk.com/kb/02-07-control-tests-and-evidence-collection) tie results to individual executions. | **Proposed:** requirement and control catalogs with many-to-many coverage; an auditable test execution and evidence revision are distinct from a claim of compliance. Preserve attachment bytes, checksums, source, observation date, expiry, provenance and access controls. A dashboard must expose uncovered and untested requirements. |
| Approvals, audit history and indicators | CISO Assistant documents [risk-acceptance approval](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/concepts/risk-assessments.md). Its [edition matrix](https://intuitem.com/compare) reserves queryable audit log and per-object trail for Pro. | **Proposed:** local owner/status in phase 4 is descriptive; authoritative approval, actor identity, immutable release/version history and audit belong to phase 7 server governance. Phase-5 indicators carry target, value, unit, source/date and measurement kind (manual, simulated, observed); coverage is not evidence of effectiveness. Do not imply Community's Pro audit trail is available. |

These are design inferences from sources, **not** claims that Lila already implements them. Phase 4 should explicitly cover both operational loss and cybersecurity scenarios while allowing a control to support either. A process owner may assess delivery risk without assigning a CVE or a threat taxonomy. Conversely, cyber assets and threats should remain linkable without forcing every risk into a BPMN activity.

## Interchange and execution path

1. **Phase 1–2 foundation:** settle repository identity, object versions, typed links, attachment storage and reverse lookup in RM-01. Preserve BPMN IDs and model identity. The current archive (version 1 and the multi-process version 2) drops unknown entries; do not use it as an evidence transfer format. [Roadmap](../ROADMAP.md), [project format](../PROJECT_FORMAT.md).
2. **Phase 4 GRC contract:** define assessment-scale revisions, risk states, control effectiveness/test records, requirement coverage, evidence revisions and treatments using synthetic operational and cyber cases. Keep simulation outputs labeled as simulated observations, never as control tests.
3. **Phase 7 authority:** add approval and audit through authenticated server operations. A copied local file cannot substantiate who approved a risk acceptance. Define access rules for sensitive evidence and portable export before any connector.
4. **Phase 8 optional CISO adapter:** exchange a documented mapping through its [REST API](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/integrations/api.md) using instance-scoped token auth. Map Lila's stable IDs to remote IDs, matrix revisions, attachments and links; test create/update/delete, conflicts, pagination, permission failures and round-trip losses on a **pinned Community release**. CISO Assistant's custom [library authoring](https://github.com/intuitem/ciso-assistant-community/blob/main/product-docs/configuration/libraries/custom-libraries.md) uses XLSX to author and YAML to import/export frameworks, matrices and mappings. That YAML is vendor-specific; it is not Lila's canonical schema. Pro-only domain import/export and import wizard must not be assumed.
5. **Phase 8 optional execution adapter:** test a pinned Flowable Open Source deployment with [BPMN deployment/start/task REST calls](https://www.flowable.com/open-source/docs/bpmn/ch02-GettingStarted) and the [DMN REST API](https://www.flowable.com/open-source/docs/dmn/ch07-REST). Define deployment identity, environment, security, variable mapping, form/task behavior, runtime event provenance and failure recovery. Compare the imported and exported BPMN and reject unsupported executable constructs explicitly. This does not make Lila a workflow engine; DMN authoring/interchange awaits its own ADR.
6. **Future format study:** [OSCAL](https://pages.nist.gov/OSCAL/) is a candidate for security-control exchanges when a concrete consumer exists. Test exact model/version and preserved fields; avoid implying that any CISO Assistant or Lila export is OSCAL today.

## Open questions and acceptance evidence

- Which risk values are assessed independently, and which (if any) are calculated? Who may override them, and what evidence demonstrates a control's *operating* effectiveness? Decide in the phase-4 contract before implementing heatmaps.
- Is “residual” a measured current exposure after controls or a forecast after planned treatment? The CISO Assistant three-state model is useful precisely because it avoids this ambiguity.
- Which operational contexts besides processes and assets are first-class: products, suppliers, locations, safety, quality, finance? Define typed relations incrementally without imposing cybersecurity vocabulary on every risk.
- For an external CISO Assistant adapter, which edition/version and exact endpoints support required fields, attachment transfer, conflict detection and export? A documentation page or API schema alone is insufficient; preserve a tested fixture and loss report.
- Obtain Eramba Community's **current application license text** and live edition entitlements before classifying it as OSS or planning an API adapter. Its private source repo and free/open marketing language do not answer this.
- Resolve SimpleRisk's API-Core contradiction for a pinned release and paid Extras contract before considering integration. Confirm whether the desired mapping can be made without its paid API or Import-Export Extra.
- For Flowable, which subset of Lila BPMN can run without vendor extensions, and what content survives deploy/retrieve? Validate actual engine runtime and authorization, not just BPMN XML syntax.

**Validation for this research:** primary vendor/repository and NIST sources were read on 2026-09-26. No product was installed; no live edition, license grant, API call, file round trip or execution smoke test was performed. Feature claims are qualified accordingly. Recheck version and edition boundaries before implementation.
